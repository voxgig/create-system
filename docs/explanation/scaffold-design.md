# Explanation: scaffold design

*An explanation — why the scaffold is shaped this way.*

## Empty, but complete

The generated project has the full structure — model, environments,
generation wiring, tests — and no content. This is deliberate: structure
is hard to retrofit and cheap to ship, while content (entities, services)
is the user's domain. The commented `thing` example keeps the path from
empty to working a one-step edit (uncomment), instead of a docs hunt.

## The scaffold is itself generated

`src/part/*` are [jostraca](https://github.com/jostraca/jostraca)
components; `scaffold.ts` composes them. Using the same templating
machinery the Voxgig stack uses for its own codegen keeps one mental
model, and lets parts share slots (the project name flows into config,
branding, and docs from a single value).

## Scaffold-once vs. model-driven

`create-system` runs once; from then on the project evolves through its
*model* (`voxgig-system add ...` + `npm run model-build`). That split
keeps the scaffolder small — it does not need upgrade logic, because
everything that changes over a project's life is either model-derived
(regenerated) or developer-owned (create-once). The web app, notably, is
not scaffolded here: it is generated by `@voxgig/build` EnvWeb when the
model declares a `web` environment, so it always reflects the current
model rather than a scaffold-time snapshot.

## Docs ship with the project

The scaffold generates a `docs/` tree and an agent guide *for the
generated project* — documentation of the app the user now owns, not of
the tooling. Rationale: a generated codebase is exactly the kind of code
whose conventions are non-obvious to newcomers (human or agent), because
the reasoning lives in the generator. Shipping the docs with the code
closes that gap at the moment it is widest.
